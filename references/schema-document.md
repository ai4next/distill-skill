# document schema · 文档蒸馏

> 用于蒸馏**一份文档或一个语料集**（论文、书、代码库、会议纪要、聊天记录、公司内部文档）。产出物是「这份材料到底主张了什么、靠什么支撑、哪里不自洽」的可追溯认知骨架。

适用对象：单篇长文档、一组同源文档（语料集）、代码仓库。
与 person / topic 的根本差异：**材料有边界**——不需要判断代表性，只需要把边界内的东西挖干净。

## 一、维度划分（6 维）

| 编号 | 维度 | 文件 | 搜索/提取目标 |
|------|------|------|--------------|
| 01 | 论点树 | `01-argument-tree.md` | 主张及其层级：主论点 → 支撑论点 → 子主张 |
| 02 | 证据链 | `02-evidence-chain.md` | 每个论点的支撑物：数据、引文、实验、先例、代码 |
| 03 | 术语表 | `03-glossary.md` | 文档自造或重新定义的术语，及**全文用法是否一致** |
| 04 | 隐含假设 | `04-assumptions.md` | 未被说出但必须成立的前提 |
| 05 | 内部矛盾 | `05-contradictions.md` | 文档内部前后不一致之处 |
| 06 | 信息缺口 | `06-gaps.md` | 文档**声称要回答但没回答**的问题，以及明显该提却没提的 |

### 01 论点树
- **提取重点**：**层级关系**。区分主论点（删掉它全文垮掉）与支撑论点（删掉它主论点变弱）。这正是去水三问第 1 问在文档上的用法。
- **常见陷阱**：❌ 按章节顺序抄标题当论点树——文档的叙述顺序 ≠ 论证结构，蒸馏是**重组**。

### 02 证据链
- **提取重点**：**证据强度与论点强度的匹配度**。强论点 + 弱证据 = 关键发现，必须标出。
- **常见陷阱**：❌ 只记「有证据」不记证据类型；❌ 把作者的观点转述当作证据。

### 03 术语表
- **提取重点**：**一词多义与前后不一致**。作者在第 2 节和第 7 节用同一个词指两件事，是内部矛盾的常见来源。
- **常见陷阱**：❌ 抄词典定义——术语表只收**本文档的用法**。

### 04 隐含假设
- **提取重点**：**结论成立必须为真、但全文未论证的前提**。这类前提一旦被推翻，整份文档失效。
- **常见陷阱**：❌ 把「作者没说」等同于「作者假设」——隐含假设须是**逻辑上必需**的，不是随便猜的。

### 05 内部矛盾
- **提取重点**：矛盾三类的判定（时间性 / 领域性 / 本质性张力）。文档内部的矛盾多为**领域性**（不同章节面向不同受众）与**本质性张力**。
- **常见陷阱**：❌ 调和（见 `distillation-framework.md` 第五节错误处理清单）；❌ 把作者明确标注的「此处有争议」当成作者自己的矛盾。

### 06 信息缺口
- **提取重点**：**承诺-交付差**——摘要/引言承诺要回答的问题，正文是否回答了。
- **常见陷阱**：❌ 把「我没读到」写成缺口；缺口须是文档范围内应该覆盖而缺失的。

## 二、三重验证的改造

| 三重验证（原） | document schema 中的改造 |
|---------------|------------------------|
| 验证 1 跨域复现 | **跨章节复现**：同一主张在 ≥2 个独立章节/模块出现 |
| 验证 2 生成力 | **可执行性**：能否据此文档推断出对未覆盖场景的具体做法 |
| 验证 3 排他性 | **文本内证据密度**：该主张在文档内有独立证据支撑，而非重复陈述 |

**信度四级（A/B/C/D）在文档语境下重定义**：

| 等级 | 文档语境含义 |
|------|-------------|
| **A** | 文档原文直引，可定位到章节/行号/文件路径 |
| **B** | 文档内明确指向但需转述的内容（图表、代码行为、附录） |
| **C** | 文档引用的外部材料，未在文档内验证 |
| **D** | 蒸馏者的推断，文档无直接支持，须显式标「（推断）」 |

## 三、schema 专属正文段

插入位置：`DISTILLATE.md` 正文的「核心骨架」之后、「矛盾与张力」之前。

```markdown
## 论点树（含层级）
- **主论点**：…（A）
  - 支撑论点 1：…（A）
    - 子主张 1.1：…（B）
  - 支撑论点 2：…（C，证据弱）

## 证据链映射
| 论点 | 证据 | 证据类型 | 强度 | 位置 | 信度 |

## 术语表
| 术语 | 本文档定义 | 出现位置 | 前后是否一致 | 与通行定义的差异 |

## 隐含假设清单
| 假设 | 为何必需 | 若被推翻则 | 信度 |

## 可执行结论
[从文档中提取的、可直接行动的结论清单；每条注明是文档明确主张还是蒸馏者推断]
```

**硬性要求**：
- 「论点树」必须体现**层级**（缩进或编号），不允许平铺。主论点 1 条，支撑论点 3-7 条。
- 「证据链映射」中，**每个主论点至少一条证据**；无证据的论点标 `（无论证）`，这本身就是重要发现。
- 「隐含假设清单」每条须填「若被推翻则」——填不出来说明它其实不是必需假设，删除。
- 「可执行结论」是 document schema 相对其他 schema 的**独有交付物**：其他 schema 交付认知，本 schema 交付行动。

## 四、特殊情形：代码库作为文档

代码库按 document schema 蒸馏，两个维度换名换义：

| 维度 | 代码库中的含义 |
|------|--------------|
| 01 论点树 → **架构决策树** | 每个 ADR（架构决策记录）是一个论点：父节点 = 约束（性能/成本/合规），子节点 = 在约束下的选型。主论点 = 这套架构要解决的核心矛盾 |
| 02 证据链 → **测试与调用点** | 论点是否被支撑，看测试覆盖与真实调用点：有测试 = A 级证据；有调用无测试 = B 级；只在文档里写着 = D 级 |
| 03 术语表 | 领域模型词汇（实体名、状态机名），检查是否一处一义 |
| 04 隐含假设 | 未写进 README 但代码强依赖的前提（单机部署、时钟同步、上游幂等） |
| 05 内部矛盾 | 文档与实现不一致、两处实现同一逻辑但行为不同 |
| 06 信息缺口 | 无测试覆盖的路径、TODO/FIXME、无人维护的模块 |

**证据类型取值**（`sources[].type` 用 `code`）：`测试用例` / `调用点` / `提交历史` / `注释与文档` / `配置`。

**代码库特有的陷阱**：❌ 把 `README` 的自述当作架构事实（README 常滞后于实现）；✅ 以调用点与测试为准，README 只作对照物。❌ 把「能跑」当作论点被验证——能跑只证明主路径成立。

## 五、质检

- [ ] 论点树有层级，且主论点唯一、可被一句话说出？
- [ ] 每个主论点都有证据映射；无论证的已标 `（无论证）`？
- [ ] 术语表记录的是**本文档用法**，并检查了前后一致性？
- [ ] 隐含假设每条都填得出「若被推翻则」？
- [ ] 内部矛盾分了类型，且**没有被调和**？
- [ ] 信息缺口包含「承诺-交付差」（引言承诺 vs 正文交付）？
- [ ] 可执行结论区分了「文档主张」与「蒸馏者推断」？
- [ ] 每条都带信度，D 级占比 <20%？
